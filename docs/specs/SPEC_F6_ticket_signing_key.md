## How to read this spec

The plain point first. The dashboard gives a viewer's page a **ticket**: a short signed note saying "this person may
use the report service for five minutes". The report service believes the name in the ticket, and that name becomes
the run's "Generated by" in the evidence. Today the ticket is signed with the **service token**, the same secret the
schedule Jobs and the dashboard's poller send as `Authorization: Bearer`. So anyone who holds the token (a schedule
Job's pod, anyone who can read that Secret or exec into that Job) can sign a ticket naming any person. This spec gives
tickets a key of their own, the **ticket key**, held only by the two pods that need it: the dashboard signs with it,
the report pod verifies with it. The schedule Jobs keep the token and never see the ticket key.

§1 is the mandate. §2 is the research: sources, the code, the measurements. §2a weighs the alternatives. §3 is the
design, one rule per subsection with its reason. §4 maps each Definition-of-Done item to a test and records the
proof. §5 is the walk on the lab. §6 is what an operator sees. §7 is the change as implementation blocks
(`docs/specs/README.md`, "Implementation blocks"), applied with

    python3 local-development/apply-spec-blocks.py docs/specs/SPEC_F6_ticket_signing_key.md . --apply

Line citations into the code at `8833eab5` (the same lines as `851ea909` for every file cited) are file:line in plain text; prose cites `path#anchor`.

## 1. The mandate, and what is out of scope

The mandate (#392, "The change", "Must not change" and "Definition of Done"): sign tickets with a key that only the
dashboard holds, separate from the service bearer; research how the dashboard and the report pod receive their
secrets today (the chart's secrets mint Job) and how the new key is rotated. Must not change: existing tickets keep
working through one rotation window; the report service's other authentication stays as it is. Done: a test that
forges a ticket with the service token fails before the change and is refused after; rotation documented and
tested; the chart creates the key (a secrets mint) with a version bump, rendered RBAC before and after, REMOVED 0;
reviewed by two seats; on CRC a forged ticket is refused and a real one works. #131's decision 4 (2026-09-16) is the
origin: "a focused follow-up PR splits the ticket-signing key from the service bearer (fixes the today-existing
attribution-forgery: a token holder minting a viewer ticket → a fabricated human name in the `report_run` evidence
table)".

Out of scope: a key id or JWT/JWS envelope (§2a, C), automatic rotation (a CronJob that rotates; the operator rotates
by hand, §3.4), re-reading a rotated key without a restart (§3.4), the service token's own rotation (it is unchanged,
and so is its 0.37.0 carry-over), and the report service's other doors (the bearer, the probes), which §3.7 holds as
they are.

## 3. The design

### 3.1 The scheme: HMAC-SHA256 with a key of its own

Rule: a ticket is signed and verified with the ticket key; the service token never verifies a ticket and the ticket
key is never a bearer. Reason: the forgery exists because one secret does both jobs (server.py:89, :142, :149); the
schedule Jobs need the bearer and must not be able to sign. HMAC rather than Ed25519 (§2a, A and B): the only verifier
is the report pod, which writes the evidence itself, so a verifier that cannot sign protects nothing in this topology,
and HMAC is `hmac`/`hashlib` from the stdlib the code already uses (ticket.py:7-8). A key with the token's bytes is
refused at startup in both pods (`load_ticket_keys`), because a hand-made Secret copied from the token would silently
reopen the hole.

### 3.2 The key: form, size, where it lives, who mounts it

Rule: `<reportName>-ticket-key`, data key `key`, 48 characters from `[A-Za-z0-9]`, created by the secrets-mint hook
with the token's own `random` function, only if absent, never carried over from another Secret (an empty LEGACY in
`mint`). Mounted read-only (0440) at `/etc/gsd/report-ticket`: in the dashboard Deployment (and its recovery twin)
with `items: [key]` only, because the dashboard signs and never needs `previous`; in the report Deployment whole, so
a rotation's `previous` appears there. Never in a schedule CronJob (T392-6 renders two schedules, one delivering, and
asserts neither mounts it). Reason: 48 × log2(62) ≈ 285.8 bits ≥ the 256 RFC 7518 §3.2 requires, and longer than
RFC 2104 §3's L; the hook's create-if-absent is measured to keep a Secret across upgrades (§2.3); `load_secret`
already refuses anything under 32 bytes.

### 3.3 The format, the verification order, and every refusal

Rule: a version-2 ticket is `v2.<base64url payload>.<base64url HMAC-SHA256>`, the payload's `v` is 2. The report
service checks, in this order, answering as shown:

| Step | Check | Refusal | Status (as today unless marked) |
|---|---|---|---|
| 0 | a bearer is present | the bearer is not the service token | 401 "service token does not match" (unchanged) |
| 1 | a ticket header is present | none | 401 "a report ticket is required" (unchanged) |
| 2 | the shape | two dot-separated parts: a version-1 ticket | **401 "ticket is from an earlier release; mint a new ticket" (new)** |
| 3 | the shape | not three parts, or the prefix is not `v2` | 403, the gate's sentence |
| 4 | strict base64url (one spelling) | — | 403 |
| 5 | the signature, under `current`, then under `previous` when a rotation is open | neither verifies | 403 |
| 6 | the claims: JSON, `v` = 2, `iat`/`exp` integers, lifetime ≤ 3600, issued ≤ 30 s ahead | — | 403 |
| 7 | expiry | expired | 401 "the report ticket expired; mint a new ticket" (unchanged) |
| 8 | `tier` = all, `viewer` = `X-Forwarded-User` | — | 403 |

Reason: the prefix is the explicit typing of RFC 8725 §3.11, read before any byte is decoded, so nothing unsigned is
parsed (step 2 needs no JSON); the signature precedes the claims as before. A version-1 ticket is a 401 because it
grants nothing either way and a 401 is what makes an open page mint a fresh ticket (index.html:2781) instead of
showing an administrator the refusal card. No key id (§2a, C): two HMACs at most.

### 3.4 Rotation, and the one rotation window

Rule: the operator rotates with the chart README's two commands ("Rotating the report ticket key", Block 70). The
first moves `key` to `previous`, writes a fresh 48-character `key`, restarts the report pod and waits for it, then
restarts the dashboard. The report pod then verifies with both keys while the dashboard still signs with the old
one, and with both while pages hold tickets signed before the dashboard's restart. The second, one ticket lifetime
later (`reporting.ticket.ttlSeconds`, 300 s by default, at most 3600) after the dashboard is ready, removes
`previous` and restarts the report pod. That interval is the one rotation window: every ticket signed with the old
key has expired by its end, because `verify` refuses `exp <= now` and a ticket lives at most the TTL. The values are
read into the shell and written by `oc patch`; nothing prints them (T392-7 runs both commands under a recording `oc`
and asserts it). Both pods read their keys once, at startup (`build_report_app`, `build_app`), as they read the token
today, so the restarts, not the kubelet's refresh of a mounted Secret, decide when a key takes effect. The report
pod's start line says `ticket key loaded; a previous key too: a rotation is open` while the window is open.

### 3.5 Compatibility during the rolling upgrade

The two Deployments roll together on an upgrade (both `Recreate`, one replica, measured on the lab: `oc get deploy -n group-sync-dashboard` prints `group-sync-dashboard Recreate 1` and `group-sync-dashboard-report Recreate 1`).

| Dashboard | Report pod | A page's ticket | Result |
|---|---|---|---|
| old (signs v1 with the token) | new | v1 | 401 → the page mints once → v1 again → the error until the dashboard is ready |
| new (signs v2 with the key) | old (verifies with the token) | v2 | the old verifier reads `v2` as the payload, not base64url → 403, the refusal card until the report pod is ready |
| new | new | v2 | works; a ticket held from before the upgrade (v1) → 401 → minted afresh → works |

Rule: no window in which a version-1 ticket verifies. Reason: a version-1 ticket was signed with the service token,
so the forger's and the dashboard's are the same bytes; accepting one is accepting the other. The cost is the mixed
rows above, which last as long as the two pods take to restart (not measured; §5 records it on the lab). A rollback
to 4.4.0 returns both pods to signing and verifying with the token; the ticket-key Secret stays, unread, and the
next upgrade finds it and keeps it.

### 3.6 The chart

The hook's Role gains `get` on `<reportName>-ticket-key` (`create` is already unscoped); its Job gains
`TICKET_SECRET` and one line, `mint "$TICKET_SECRET" "" key 48`, behind the token's own switch (`MINT_TOKEN`,

def verify(keys: TicketKeys, ticket: str, forwarded_user: str | None, now: float | None = None) -> dict:
    """Return valid claims; refuse malformed, misbound, expired or future-dated tickets.

    The order is SPEC_F6 §3.3's: the shape (a version-1 ticket is told to mint again), the encoding, the signature
    under the current key and then the previous one, and only then the claims, so nothing unsigned is parsed."""
    parts = (ticket or "").split(".")
    if len(parts) == 2:
        raise TicketError(EARLIER_FORMAT)
    if len(parts) != 3 or parts[0] != _PREFIX:
        raise TicketError("ticket missing or malformed")
    try:
        payload = _unb64(parts[1])
        signature = _unb64(parts[2])
    except (ValueError, TypeError) as exc:
        raise TicketError("ticket is not base64url") from exc
    if not any(hmac.compare_digest(signature, _sign(key, payload)) for key in (keys.current, keys.previous) if key):
        raise TicketError("ticket signature does not verify with the ticket key")

```markdown
**Upgrading to 0.69.0: the ticket key (#392).** A viewer's ticket is signed with a key of its own,
`<reportName>-ticket-key` (key `key`), and no longer with the service token, which the schedule Jobs hold too: before,
anyone holding the token could sign a ticket naming any person, and that name became the run's "Generated by". The
`secrets-mint` hook creates the key once, 48 random characters, and never overwrites it; the dashboard and the report
pod mount it, a schedule Job never does. With `secretsMint.enabled=false`, create it before upgrading (32 bytes or
more, not the token's value), or the two pods cannot start. A page open across the upgrade holds a ticket of the
earlier format: the report service answers it with 401 and the page mints a fresh one. While one pod runs the new
version and the other the old one, for the seconds the two take to restart, the Reports tab may refuse a viewer;
it works again once both are ready.

#### Rotating the report ticket key

Rotate it when it may have leaked, or on your schedule. The current value moves to `previous`, which the report pod
also verifies with, and a new value becomes `key`. Restart the report pod first, then the dashboard: while the
dashboard still signs with the old key the report pod already accepts both, so no open page is refused. The values
are read into the shell and written by `oc patch`; nothing prints them.

<!-- rotate the ticket key, open the window -->
````bash
NS=group-sync-dashboard
KEY_SECRET=group-sync-dashboard-report-ticket-key
OLD="$(oc get secret "${KEY_SECRET}" -n "${NS}" -o jsonpath='{.data.key}')"
NEW="$(head -c 96 /dev/urandom | base64 | tr -dc 'A-Za-z0-9' | cut -c1-48 | tr -d '\n' | base64)"
if [ -n "${OLD}" ]; then
  oc patch secret "${KEY_SECRET}" -n "${NS}" --type=json \
    -p "[{\"op\":\"add\",\"path\":\"/data/previous\",\"value\":\"${OLD}\"},{\"op\":\"replace\",\"path\":\"/data/key\",\"value\":\"${NEW}\"}]"
else
  echo "${KEY_SECRET} has no key to rotate" >&2
fi
unset OLD NEW
oc rollout restart deployment/group-sync-dashboard-report -n "${NS}"
oc rollout status deployment/group-sync-dashboard-report -n "${NS}" --timeout=300s
oc rollout restart deployment/group-sync-dashboard -n "${NS}"
oc rollout status deployment/group-sync-dashboard -n "${NS}" --timeout=300s
````

default and at most 3600) after the dashboard is ready again: every ticket signed with the old key has expired by

- `GET /api/report/ticket` on the dashboard calls `require_admin_tier(request)` (`local-development/gsd/api.py#require_admin_tier`) — a refusal is the same 403 with the same "For administrators only." sentence — and returns `{"ticket": "<payload>.<sig>", "expires_in": 300, "prefix": "/report"}`. It is a **pure function of the request** — no store write, no file, no network beyond the tier check `whoami` already makes — so it satisfies "a GET on the dashboard must not cause work" in the sense R6 protects: nothing is created, rendered or stored.
- The browser sends the ticket on **every** request to `/report/**` as `X-GSD-Report-Ticket`. The report service verifies the signature, the expiry, `tier == "all"`, and that `viewer` **equals the proxy-stamped `X-Forwarded-User` on that request** — the ticket is bound to the session identity it was minted for, so a captured ticket is useless from another session. A custom header also makes the `POST` a non-simple request, which is the CSRF defence.
- With `visibility.enabled=false` every authenticated reader is wide (`local-development/gsd/api.py#viewer_scope` returns `TIER_ALL` when restrictions are off), so every reader can generate — the existing semantics, stated. With the proxy off the chart refuses to render (§2).

A **self-tier reader cannot fetch a report through the internal name**: they cannot obtain a ticket (403 at `/api/report/ticket`), the report service refuses every `/report/api/*` request without a valid ticket or the service credential, and the NetworkPolicy (§5.4) means a self-tier reader's own workloads elsewhere on the cluster cannot reach the report pod's port at all.
