group-sync-dashboard · design decision · 2026-09-23

Who decides your access on a remote cluster?

You are cluster-admin on the lab. On dashboard you see everything; on shared-rnd and shared-qa you see only your own rows. Both remotes are configured self-only, so nobody is asked. The remote could answer this itself, and today our code will not let it.

The three answers the dashboard can give today

The sign-in is always on the host, through the oauth-proxy. What differs is which API is asked whether you may see a cluster's data wide. The question is always the same: may this person list clusterrolebindings?

The two models, defined precisely

inherit + same-as-host

The host's RBAC governs the remote's data too.

Who is asked
The host API, by the dashboard's own ServiceAccount.
The question
May you list clusterrolebindings on the host?
Your groups
Read from the host's Group objects.
identity
Has no effect on the tier. Under inherit identity is not consulted: the host's decision applies, and self rows are keyed by your host username. same-as-host here only documents intent.
Remote RBAC
None. Works with a read-only token.
True when
One team administers the whole fleet, so host admin = remote admin by policy. The lab is the extreme case: shared-rnd is the host.
Risk
A host admin sees a remote's bindings and people wide, even with no standing on that remote. That is a policy decision, made once per cluster.

remote-sar + same-as-host

Each cluster's own RBAC decides who sees it wide.

Who is asked
The remote API, with the token that joined the cluster.
The question
May your username list clusterrolebindings on that remote?
Your groups
Read from the remote's Group objects.
identity
Load-bearing. Your host username is sent to the remote, so it must name the same person there. The chart refuses remote-sar without same-as-host.
Remote RBAC
The joining SA needs create subjectaccessreviews and list groups. Measured on the lab: both joining SAs have them (ClusterRole group-sync-dashboard-cluster-poller).
True when
Clusters share one identity provider (LDAP): one uid, one person.
Risk
htpasswd users (and kube:admin) are per-cluster people. The same name on two clusters is two accounts, so a name match is not proof.

Why it worked before

  • Until 2026-09-22 shared-rnd was a hand-made Secret with visibility: inherit and identity: same-as-host (docs/examples/cluster-secret-shared-rnd.redacted.yaml).
  • #307 replaced it with a saTokenLookup stanza and deliberately declared no visibility, so it took the default, self-only. That changed your access without being raised as a decision.
  • shared-qa is a hand-made Secret from #310's testing with no visibility key, so it has always been self-only.
  • Your lab kubeadmin is an htpasswd user (identity developer:kubeadmin). On a real remote, that name would be a different person.

What is supported today

saTokenLookup (the lookup writes a Secret)yesrefusedyesyes

Why refused: the per-cluster resolver that asks the remote is built once, at start-up, from the values list (gsd/api.py). A Secret-declared cluster appears at runtime and never gets one. The parser says so: "remote-sar for a Secret-sourced cluster is S2". That work was never done, and it is the gap that bit you: the way we now join clusters is exactly the way that cannot ask the remote.

Decisions to make

D1 · the gap
Support remote-sar for every way a cluster is joined.
Build the remote resolver when discovery finds the cluster, rebuild it when the Secret's credential changes, drop it when the cluster is retired. Accept remote-sar from a Secret and from a saTokenLookup stanza.
Recommend: yes. Without it, the only choices for a looked-up remote are "the host decides" or "nobody is wide".
D2 · the default for a newly joined remote
self-only (today), or remote-sar?
self-only: safe and silent. Nobody is wide until someone configures it, which is what just surprised you.remote-sar: the remote's RBAC answers for each reader. The joining SA already has the rights (measured). If it lacks them, every reader gets self and the cluster shows a finding.
Recommend: remote-sar, with D4's finding, so that "narrowed" always has a reason.
D3 · what "same person" means (identity)
Is your host username trusted as the same person on the remote?
(a) Every username: simple. On the lab, kubeadmin is wide on shared-rnd. On a real estate, an htpasswd developer on the host would be read as the remote's developer.(b) Directory identities only: accounts from the break-glass providers (loginCapture.htpasswdProviders, e.g. developer) are never mapped across clusters. LDAP users are.
Your call. (b) is the correct rule for real estates, but it narrows this lab's htpasswd kubeadmin on shared-rnd. An LDAP admin would be wide. (a) matches what you expected today.
D4 · when the joining SA may not ask
A 403 on the review: silent self, or a named finding?
Show it on the Cluster Configurations tab and in the cluster selector: "this cluster cannot check access: grant create subjectaccessreviews to <SA>".
Recommend: a finding. Self for everyone, with the reason and the fix named.
D5 · say why you are narrowed
Should the page say which rule decided your view of this cluster?
One line under the cluster selector: the host decides · shared-rnd says you may see everything · shared-rnd says: your own rows · shared-rnd cannot check access · this cluster is self-only.
Recommend: yes. Today the page narrowed you and gave no reason, which is how this looked like a bug.
D6 · the lab, right now
Until D1 ships, what should shared-rnd and shared-qa be?
inherit + same-as-host restores what you had before #307, and is literally true on this lab (same cluster, same identity provider). Switch to remote-sar once D1 lands. shared-qa: the same, or remove it if it was only #310's test cluster.
Recommend: inherit now, remote-sar after D1.

How this fits the cluster-admin tier (#322)

You ruled today that passing clusterAdminSar grants every tier the host decides, and that per-cluster policies still apply. Under this design that reads cleanly: on inherit clusters a host cluster-admin is wide; on remote-sar clusters the remote's own answer about you stands, because being admin on the host is not proof on another cluster; self-only and hidden are unchanged.
